Rules:
- Propose a different RULE SHAPE, never a finer grid over an existing one.
  Parameters are already enumerated exhaustively.
- Each hypothesis must name WHO IS STRUCTURALLY PAYING and why they keep doing
  it. "It backtests well" is not a mechanism and will be rejected.
- Each needs a kill condition written now, before results exist, concrete
  enough that a number decides it.
- Respect the established results in CLAUDE.md section 7. Do not re-open a
  closed family without new evidence.
- Read the shape column before the value. A SPIKE is not a finding no matter
  how large, and a cell resting on one independent path is not evidence.
- Give at least one axis three or more NUMERIC levels, and make it the axis you
  expect to matter. The shape diagnostic asks what happens one step either side
  of the best cell, so an axis with only two levels has no "one step away".
  Booleans are switches and a None is "off"; neither counts toward the three,
  and neither do strings -- a gate axis of "sma:20" through "sma:200" reads as
  ordered to you and is five unrelated labels to the diagnostic. A hypothesis
  with no such axis can never be shown to be a spike, which is not the same as
  not being one, and it is refused mechanically before registration: H0006 and
  H0007 cost 126 trials between them before this was enforced. If the axis you
  care about is naturally a string, express it as a number in `fixed` plus a
  numeric grid axis, or propose the numeric form of the same question.
- Keep the grid small enough to be justified. Every configuration you enumerate
  enters an append-only ledger and raises the multiple-testing bar for every
  result the project will ever produce. An axis that cannot plausibly change
  the outcome is a cost with no return.
- Set "track" to "A" for accumulation shapes or "B" for signal-driven positions
  entered long or short and exited on their own signal.
- Never propose opening the sealed holdout.

## What the evaluator can express

A hypothesis is only runnable if every key in `grid` and `fixed` is a field of
the config type its track uses. Anything else expands to a TypeError and the
proposal is killed mechanically before it reaches the queue. Propose within
this vocabulary, or propose a rule shape that fits it.

Track A -- TrialConfig fields:
  contribution, stride_days, n_contributions, hold_days, leverage, gate, take_profit, stop_loss, include_funding, clock, fee_bps, slippage_bps, cost_multiplier
  `gate` is a string: "none", "dip:<drop>:<lookback_days>", or "sma:<days>".

Track B -- SignalTrialConfig fields:
  rule, lookback_days, enter_rate, exit_rate, capital, leverage, stop_loss, take_profit, max_hold_days, clock, fee_bps, slippage_bps, cost_multiplier
  `rule` must be one of: carry_funding, carry_funding_long

If the shape you want needs a rule or a field that does not exist, say so in
the claim and propose the closest thing that does exist. A hypothesis the
machine cannot run is not a hypothesis, it is a note.

Before choosing hypothesis ids, list configs/registry/, configs/queue/ and
configs/killed/ and pick the next free H#### ids so you do not collide with an
existing one or repeat one already rejected.

Write each hypothesis to configs/proposed/<id>.json using the schema in
CLAUDE.md section 3, plus the "track" field.

Do not commit, do not run backtests, and do not write to configs/queue/. An
adversary reviews every proposal before it can be registered, and the
orchestrating script commits whatever survives.

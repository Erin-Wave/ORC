# 파이프라인 — 질문이 답이 되어 눈에 보이기까지

이 문서는 **고치기 전에 읽는 지도**다. 2026-09-04 하루에 이 영역을 국소적으로
네 번 수정했고, 네 번 모두 "수정 → 예상 못 한 결과 발견 → 또 수정"이었다.
문제는 수정의 크기가 아니라 **수정 전에 경로 전체를 보지 않은 것**이었다.

| 오늘의 사고 | 국소적으로 보면 | 실제로 무엇을 건드렸나 |
|---|---|---|
| `.git/hooks` 존재를 단정한 테스트 | 테스트 한 줄 | `orc-cycle`의 **테스트 게이트**를 빨갛게 만들어 **연구를 2시간 정지** |
| CI에 `pytest tests -q` 무조건 실행 | 스텝 한 줄 | 러너에 `facts/`가 없다는 사실은 뮤테이션 스텝에만 반영돼 있었음 |
| `git reset --soft HEAD~1`로 인덱스 재현 | 스텝 한 줄 | 뒤 스텝의 `HEAD~1 HEAD` diff가 엉뚱한 쌍을 비교 → **초록인데 검사 건너뜀** |
| 커밋 로직을 `commit_results.py`로 추출 | 파일 하나 | 상주 창 스텝에 **머지 정책 사본이 하나 더** 있었음 |

그래서 이 파일에는 단계, 각 단계의 소유자, 불변식, 그리고 **이 경로를 고칠 때
반드시 확인할 목록**이 있다.

---

## 1. 단계

```
 (A) 제안            워크스테이션 supervisor → reasoning.py
                     configs/proposed/ → 적대자 거부권 → configs/queue/
                     스스로 커밋·푸시한다 (N을 올리는 유일한 커밋)
        │
 (B) 등록 + 평가     orc-cycle 잡 (6시간 크론 + dispatch)
                     ├ 패널 내려받기 (봉인 이전 구간만 담긴 번들)
                     ├ 봉인 데이터 접근 거부 확인
                     ├ ★ Kernel test suite  ← 빨간색이면 여기서 연구가 멈춘다
                     ├ daily_cycle.py
                     │   ├ intake_queue()  큐 파일은 항상 사라진다:
                     │   │                 등록되면 unlink, 거부되면 queue/rejected/
                     │   ├ run_hypothesis() → 원장(append-only, N)
                     │   ├ 서피스 리포트 / 서치 테스트 / PBO
                     │   ├ robustness 게이트
                     │   └ TARGET.json, BRIEFING.md, NEWS.json
        │
 (C) 착지            commit_results.py  ← 머지 정책의 유일한 정의 위치
                     사이클 직후 1회, 잡 마지막에 1회
                     stage(named dirs) → commit → pull --rebase → push ×3
        │
 (D) 상주 창         forever.py --until-minutes 300 --skip reason,scout,kernel_review
                     매 tick runstate.next_action():
                       findings 차단 → 종료조건 후보 → 큐(GITHUB_ACTIONS면 cycle)
                       → reason → zero-N 작업 → rest
                     액션마다 land()로 리포트 커밋·푸시
        │
 (E) 관측            health.py (한 화면) / briefing.py (한글) / notify.py → NEWS.json
                     → GitHub 이슈, orc-watchdog(루프 밖에서 루프를 본다)
        │
 (F) 게이트          로컬: pre-commit(스위트·원장·새 파일) + commit-msg(마커)
                     원격: orc-guard — 같은 스위트, 같은 마커 검사, 뮤테이션
                     러너에는 훅이 없고 --no-verify는 존재한다: (F)-원격이 유일한
                     "에이전트가 통제하지 못하는 기계"
```

## 3. I9 — 이 지도가 찾아낸 구멍

`FAILURE_COOLDOWN_MIN`(12분)은 `ZERO_N_WORK` 루프 **안에서만** 적용된다.
`cycle` 분기는 그 루프보다 먼저 반환하므로 쿨다운이 없다. 큐가 남은 채
`daily_cycle.py`가 실패하면(패널 다운로드 실패, 크래시) 상주 창은
`WORKED_SLEEP_S = 30초`마다 같은 실패를 무한히 재시도하고, zero-N 작업은
영원히 순번을 얻지 못한다.

`intake_queue()`가 큐 파일을 항상 없애기 때문에(등록 또는 `rejected/` 이동)
"같은 파일을 영원히 다시 등록"하는 경로는 없다. 위험한 것은 **intake 이전에
죽는 실패**뿐이다 — 그리고 그것이 정확히 재시도해도 소용없는 종류다.

→ 조치: `cycle` 분기도 `FAILURE_COOLDOWN_MIN`을 통과해야 한다. 실패 후
12분 안에는 zero-N 작업으로 내려가고, 12분 뒤에 다시 시도한다.

## 4. 이 경로를 고치기 전 확인 목록

1. **이 변경이 (B)의 테스트 게이트를 통과할 수 있나?** 이 기계에만 있는 것
   (`.git/hooks`, `facts/` 9.7 GB, Windows 예약 작업, 전역 git 신원)을
   단정하는 테스트는 러너에서 실패하고 **연구를 멈춘다.** 하루에 두 번 그랬다:
   `.git/hooks` 를 단정한 테스트(오전)와 `next_action()` 을 호출하면서
   `GITHUB_ACTIONS` 와 실제 큐 내용에 의존한 테스트(오후, run 33862085374).
   러너의 조건을 그대로 흉내내서 돌려라 —
   `ORC_FACTS=<빈 디렉터리> GITHUB_ACTIONS=true python -m pytest tests -q`
   그리고 `GITHUB_ACTIONS` 는 이제 `tests/conftest.py` 가 모든 테스트에서
   해제한다: 러너에서만 켜지는 환경 변수가 테스트의 답을 정하면 안 된다.
2. **HEAD·인덱스·작업 트리를 건드리나?** 건드리면 그 스텝은 **마지막**이어야
   하고 원상복구해야 한다. 뒤에 오는 스텝은 조용히 다른 커밋을 보게 된다.
3. **`git config merge.*`를 쓰려 하나?** 정의는 `commit_results.py`에만 있다.
   사본을 만들면 둘 중 하나가 표류하고, 표류한 쪽이 실행된다.
4. **새 액션인가?** `plan()`, `TIMEOUTS_S`, `DONE_EXIT_CODES`,
   `COMMIT_PATHS`, 쿨다운(I9), 그리고 zero-N인지 N을 올리는지를 모두 답해야
   한다. 하나라도 빠지면 조용히 아무 일도 하지 않거나 hot loop가 된다.
5. **워크플로에 조건 분기를 넣으려 하나?** 조용히 틀릴 수 있는 조건은
   그것이 아끼는 시간보다 비싸다(run 33845845287: 32초에 초록, 검사는 건너뜀).
   공용 저장소의 러너 시간은 무제한이다.
6. **오너 화면에 새 사실이 생기나?** `health.py`에 줄을 추가하고, 그 줄이
   다른 줄과 모순되지 않는지 확인한다(정지 시계는 **작업**을 따라가야 하고
   호출자를 따라가면 안 된다).
7. **`python scripts/mutation.py`를 돌렸나?** 커널이나 테스트를 건드렸다면
   이것이 "테스트가 아직 물고 있는가"에 답하는 유일한 방법이다.

## 5. 듀티 사이클 — "쉬지 않는다"는 주장의 실측 (2026-09-04)

`CLAUDE.md §9`는 이렇게 적어놨다: *"reports/ACTIVITY.jsonl은 감독자가 한 일
한 줄씩이다. '한 번도 쉬지 않는다'는 주장이고, 그 파일의 공백이 그것을
거짓으로 만든다."* 그 공백을 처음으로 측정했다.

```
최근 12시간   실제 작업 268분 / 구간 713분  =  37.6%
가장 긴 공백  122분
측정 시점     마지막 작업 종료 후 103분, 다음 예정 작업까지 48분
```

`scripts/watch.py`가 이 숫자를 낸다. 구간은 **합집합으로 병합**한다 — 두
감독자(워크스테이션·러너)가 같은 파일에 union으로 쓰므로 단순히 더하면 겹치는
만큼 부풀고, 이 숫자는 바로 그 주장을 검사하는 데 쓰이는 숫자다.

### 5a. 원인 A — 페이싱이 곧 정지다

`ZERO_N_WORK`의 staleness 창(scout 180분, robustness 6시간,
execution_realism 12시간, survivorship 3일, mutation 24시간)은 "이보다
자주 하지 말라"로 동작한다. 모든 항목이 신선하면 `next_action()`은 `rest`를
답하고 `IDLE_SLEEP_S = 300초`씩 낮잠을 잔다. 로그에 5분 간격 `rest` 줄이
2시간 연속으로 찍혀 있다.

**그런데 할 일이 실제로 있었다.** `execution_realism`은 트랙 B 셀을 분봉으로
다시 돌리는 작업인데, `forever.track_b_cell()`이 **첫 가족의 최고 심볼 하나만**
반환한다. 지금 서피스가 있는 (가족, 심볼) 쌍 18개 중 분봉으로 측정된 것은
**1개**(H0002/BTCUSDT)이고, **17개가 대기 중**이다. 각 실행은 235만 개
1분봉을 읽으므로 몇 분씩 걸린다 — 즉 공백을 메울 진짜 작업이 몇 시간 분량
쌓여 있는데 12시간 창이 그것을 막고 있었다.

**백로그는 `rest`만 대체해야 한다.** 첫 구현은 `execution_realism`의 floor를
20분으로 낮췄고, `ZERO_N_WORK`는 허용 시간 오름차순으로 조회되므로 가장 짧은
시계가 이겼다 — 백로그가 `scout`을 밀어냈다. scout은 이 저장소가 외부의
지불자를 들을 수 있는 유일한 경로이고(첫 여덟 가족 중 여섯이 펀딩 레이트에
얹힌 이유가 제안자가 자기 레지스트리만 재배열할 수 있었기 때문이다), 그것을
굶기는 것은 공백을 메우는 대가로 너무 크다. 기존 테스트가 이것을 잡았다.

→ `FILLER_WORK`: 허용 시간과 무관하게 **맨 마지막에** 묻는다. 정렬 키가
`(filler인가, 허용시간)`이 되어 다른 어떤 액션도 선점하지 않는다.

라운드로빈으로 아무 액션이나 돌리는 것은 답이 아니다: `robustness`는 0.1분에
끝나므로 같은 계산을 반복하는 연극이 되고, `scout`·`kernel_review`는 모델
제공자를 호출하므로 분당 호출은 비용과 `SCOUT.jsonl` 오염이다. **정직한 해법은
액션에 진짜 백로그를 주는 것**이고, 그 백로그는 `(가족, 심볼, code_hash)`로
키를 잡아야 한다 — 커널이 바뀌면 분봉 답도 바뀔 수 있으므로 백로그가 스스로
다시 열린다. 원장이 trial을 키잡는 방식과 같다.

### 5b. 정정 — "좀비 감독자"는 없었다

`watch.py`를 처음 돌리자마자 `forever.py`가 두 개 보였고, 나는 그것을 19시간
멈춘 좀비 감독자라고 적고 커밋 메시지에 넣고 그 근거로 두 프로세스를 죽였다.
**틀렸다.** 사실은 이렇다.

```
54120  parent 15948 (wscript.exe)   <- WindowsApps 실행 별칭 python.exe = 런처 껍데기
20372  parent 54120                 <- 실제 인터프리터, 잠금 보유, 작업 수행
```

예약 작업은 WindowsApps 실행 별칭의 `python.exe`를 띄우고, 그것은 실제
인터프리터를 자식으로 낳고 기다린다. 둘 다 명령줄에 `forever.py`를 갖는다.
**이 워크스테이션에서 정상 감독자는 언제나 프로세스 두 개다.** 30784는
27212의 런처였다.

그리고 로그가 09-03 23:49에 끊긴 이유는 Windows 시스템 이벤트 로그가 그대로
말해준다: **Id 42 sleep 진입 00:24:14**, 그리고 06:55:26/31에 wake source.
기계가 밤새 잤고, 깨어나면서 예약 작업이 7시간 된 stale lock을 깨고 새
감독자를 띄웠다 — 즉 §5b의 "결함"은 처음부터 **설계가 의도대로 동작한
기록**이었다.

내가 한 일: 건강한 감독자와 그 런처를 죽였다. 결과는 무해했다(§5c 때문에
어차피 재시작이 필요했다). 진단은 사실이 아니었다.

**교훈, 그리고 이것이 이 절을 남겨두는 이유.** 근거는 세 가지였다 — 프로세스
두 개, 로그 중단, stale lock. 세 가지 모두 관측이었고, 셋을 하나의 이야기로
묶은 것은 **추론**이었다. 그 추론을 확인하는 데 필요한 것은 명령 두 개였다:
`ParentProcessId`와 시스템 이벤트 로그. 그것을 묻기 전에 문서에 적고 커밋하고
프로세스를 죽였다. `CLAUDE.md §10`이 정확히 이것에 대한 조항이다 — 검사되지
않은 주장.

→ 조치: `strays()`는 이제 잠금 보유자의 **프로세스 사슬**(조상·자손)을 계산하고
그 밖에 있는 forever.py만 지목한다. 사슬 밖의 두 번째 감독자는 여전히 진짜
위험이다(등록 예산을 독립적으로 읽고, `cycle` 액션이 있는 지금은 두 기계가
daily_cycle.py를 동시에 돌릴 수 있다). 다만 런처를 그것으로 오인하는 화면은
아무도 읽지 않게 되고, 그것은 검사가 없는 것보다 나쁘다.

### 5c. 원인 C — 상주 감독자는 어제 코드를 돌린다

백로그 수정을 커밋한 뒤 로그를 5분 지켜봤는데 여전히 `rest`였다. 이유는
간단하고 나쁘다: **상주 감독자는 시작할 때 `orc.runstate`를 한 번 임포트한다.**
`next_action`, `ZERO_N_WORK`, 액션의 `plan()`을 고쳐도 이미 돌고 있는
프로세스에는 반영되지 않고, 그것을 재시작할 시간별 트리거는 인스턴스가 살아
있는 동안 `0x800710E0`으로 거부된다(§5b). 즉 **수정이 며칠 잠들어 있을 수
있고, 그동안 모든 화면은 "감독자 정상"이라고 답한다.**

→ 조치: 감독자가 자기 소스의 해시를 시작 시 기록하고, 매 tick마다 다시
계산해서 달라지면 `standing down` 로그를 남기고 exit 0 한다. 재시작은
시간별 예약 작업이 한다 — 스스로 다시 실행(re-exec)하지 않는 것은 의도적이다.
감독자를 띄우는 주체는 하나여야 하고, 자기를 재시작하는 프로세스는 버그가
들어올 두 번째 문이다. 내려가는 것은 설계상 안전하다: 잠금이 풀리고,
`claim_lock()`은 stale 잠금을 깨도록 이미 만들어져 있다.

**내려갈 때는 후임을 즉시 불러야 한다.** 첫 구현은 그냥 exit 0 했고, 그러면
시간별 트리거까지 최대 1시간 아무것도 돌지 않는다 — 대체하려던 "낡은 코드"보다
나쁘다. `stand_down()`이 순서대로 한다: 박동 중지 → 잠금 해제 → 스케줄러에
즉시 시작 요청. **순서가 곧 수정이다** — 새 인스턴스가 신선한 박동을 보면
exit 3으로 물러나고, 그러면 메우려던 그 공백이 그대로 생긴다. 스케줄러가
감독자를 띄우는 유일한 주체라는 성질은 유지된다(스스로 re-exec 하지 않는다).
트리거 실패는 치명적이지 않다: 시간별 트리거가 대비책이고, 그동안 health.py의
supervisor 줄이 BAD가 되는데 그것이 사실이다.

mtime이 아니라 **내용** 해시다. 이 워크스테이션은 `core.autocrlf=true`라
체크아웃·rebase가 줄바꿈만 바꿔도 mtime이 움직이고, 그걸로 내려가면 pull
한 번에 재시작하는 감독자가 된다.

### 5e. 백로그가 남아 있으면 floor는 적용되지 않아야 한다

재시작 직후 새 감독자의 첫 결정은 `execution_realism`이었고 23초에 끝났다.
그리고 로그의 다음 줄은 다시 `rest -- 다음은 execution_realism, 19분 후`였다.
20분 floor가 **다른 항목까지** 막은 것이다. 백로그 17개에 20분 floor면 5.7시간이
걸리고, 23초짜리 작업 사이에 19분씩 쉰다.

floor의 목적은 *같은 일의 반복*을 막는 것이다. 백로그의 다음 항목은 같은 일이
아니다 — 다른 심볼, 다른 가족, 아직 아무도 재보지 않은 답이다.

→ 조치: filler는 **남은 백로그가 있으면 시계와 무관하게 due**다. floor는
백로그가 비었을 때만 의미를 갖고, 그때는 `plan()`이 None을 반환하므로 사실상
쓰이지 않는다. 실패 쿨다운(`FAILURE_COOLDOWN_MIN`)은 그대로 앞단에 남는다:
같은 항목에서 계속 실패하면 그 항목은 백로그에 남으므로, 쿨다운이 없으면
30초마다 재시도하는 hot loop가 된다(I9와 같은 함정).

`runstate`가 `scripts/forever.py`의 백로그 함수를 지연 임포트한다. 새 모듈을
만들지 않은 것은 선례를 따른 것이다 — `next_action`은 이미 같은 방식으로
`scripts/findings.py`를 읽는다.

### 5g. 백로그는 "측정 불가"도 기록해야 한다

백로그가 돌기 시작한 직후 로그에 `H0002 DOGEUSDT`가 1분에 한 번씩 반복됐다.
원인은 데이터였다: **DOGEUSDT 1분봉의 0.736 %가 결측**(한도 0.5 %)이라
`panel.load`가 정당하게 거부한다. 그 쌍은 이 기계에서 측정할 수 없다.

문제는 그 다음이다. `execution_realism.py`는 드리프트 FAIL도, 예외로 죽는
것도 **똑같이 exit 1**이었고, `DONE_EXIT_CODES`는 1을 "작업이 일어났다"로
읽는다(여기서 FAIL은 판정이므로 옳다). 그래서 크래시가 "완료"로 기록되고,
리포트에는 아무 줄도 안 남고, 쌍은 백로그에 남아 영원히 재시도됐다 — I9와
같은 hot loop인데 이번에는 쿨다운이 아니라 **결과 기록의 부재**가 원인이었다.

→ 조치, 결과 세 가지에 코드 세 개:

| 코드 | 뜻 | 기록 | 감독자가 읽는 방식 |
|---|---|---|---|
| 0 | 통과, 또는 **여기서는 측정 불가** | 남는다 | 완료 |
| 3 | 드리프트 FAIL | 남는다 | 완료 (판정이다) |
| 1 | 처리되지 않은 예외 | 없다 | 실패 → 12분 쿨다운 |

그리고 `orc.target._passed_in`은 `passed` 키가 없는 항목을 **미측정**으로
읽는다. "측정할 수 없었다"와 "통과하지 못했다"는 다른 문장이고, 후자로 읽으면
후보가 자기에게 한 번도 돌지 않은 검사에 떨어진 것으로 보고된다 —
`verdict.disqualifiers`가 반대 방향에서 거부하는 바로 그 오류의 거울상이다.

`(symbol, clock)`을 물을 때 한쪽만 미결제약정을 읽으면 서로 다른 패널이 필요한데,
그걸 무시하는 dict가 결함을 그대로 되돌린다.

| # | 불변식 | 지키는 것 |
|---|---|---|
| I18 | **채점 경로는 규칙이 필요로 하는 패널을 로드한다** | `_needs_positioning` + `test_every_scoring_path_loads_the_panel_the_rule_needs` |
| I19 | **쓴 벤더는 그 diff를 심사하지 않는다** | `diff_adversary.reviewers()` |

### 10f. 관문에 실제로 물린 것

| 어디 | 무엇 | 기본값 |
|---|---|---|
| `pre-commit` | diff 적대자 (`check_diff_adversary`) | **꺼짐**, `ORC_DIFF_ADVERSARY=1`로 켬 |
| `orc-guard` | `oracle/fuzz.py --cases 400` | `continue-on-error` |
| `orc-guard` | `mypy orc/kernel orc/eval` | `continue-on-error` |
| 스위트 | hypothesis 성질 3개 | 하드 |

**diff 적대자가 기본으로 꺼져 있는 이유**는 커밋당 모델 호출 하나를 쓰기 때문이다.
docstring 한 줄 고치는 사람이 그걸 기다릴 이유가 없다. 감독자는 켠다 — 이 관문이
존재하는 이유가 바로 그 작성자다.

**오라클이 `continue-on-error`인 이유**는 첫 불일치들이 아직 분류 중이고, 그중
하나가 **어느 구현의 결함도 아니라 사양의 구멍**이기 때문이다(§10c). 오늘 하드로
걸면 아무도 결정하지 않은 질문 위에서 모든 커밋이 막힌다. 청산 잔존이 정해지면
하드로 올린다.

**오라클 분류 결과 (2026-09-05):** 첫 5건이 **전부 같은 하나**에서 나온다. 창 안에
청산이 없으면 두 구현이 **정확히 일치한다** — 같은 거래, 같은 봉, equity 차이
`0.00e+00`. 다른 건 종료 라벨 두 개(`signal` vs `end`, `signal` vs `max_hold`)뿐이고,
진입 타이밍 차이(`fast=57 ref=56`)는 파생이다: 청산이 다른 봉에서 일어나면 다음
진입에 열리는 봉이 달라진다.

즉 1일차 오라클의 실제 산출은 **"두 구현이 아무도 답하지 않은 질문 하나를 빼면
전부 일치한다"**이다.

### 10g. 성질 검사 — 예제가 아니라 클래스

17건 전부 초록 스위트에서 발견됐고, 그것들을 덮는 테스트는 전부 **결함을 알고 난 뒤**
쓴 것이다. 후행 지표다.

성질 3개를 생성 입력 위에서 검사한다. 첫 번째가 요점이다 — **`b29a2f5e1a0d`가 위반한
성질이고, 그걸 쓰는 데 그 결함을 알 필요가 없었다:**

> 종가보다 낮은 저가는 낙폭을 **깊게만** 할 수 있다

그리고 **그 성질의 첫 버전이 변이를 통과했다.** `wicked >= flat`은 **등호로 만족**되고,
종가만 마킹하면 정확히 등호가 나온다. 하한을 함께 걸어야 죽는다. 부등식으로 쓴 성질은
양변이 같은 오답으로 무너질 때 통과한다 — 성질 테스트판 같은 결함이다.

### 10g-bis. 게이트의 첫 실전 — 그리고 그것이 잡은 것

관문을 처음으로 실제 스테이징에 물렸다. 거부를 눈으로 보려고 일부러 오류
(`x` 한 줄)를 심었는데, codex는 **그건 종속절로 말하고 다른 것을 앞세웠다:**

> `orc/kernel/metrics_fc.py:81`이 최소 관측창 거부를 `years < 0.0`으로 바꿔
> 사실상 도달 불가로 만든다. 인접 주석은 짧은 창 외삽을 거부해야 한다고 말하는데
> `cagr`가 임의로 짧은 이력을 연율화한다. **3개월 두 배가 NaN이 아니라 1500%로
> 기록된다.**

당시 트리에서 재보니 **15.02 (1502 %)** 였다.

**정정: 저장소는 옳았다.** `git show HEAD:` 는 `MIN_YEARS_TO_ANNUALISE`를 갖고
있었고, 결함은 커밋된 적 없이 **워킹트리에만** 있었다 — 변이 검증 중 복원이

**그래도 실제 위험이었다.** 스위트도 감독자도 워킹트리에서 돈다. 그 상태로

`TARGET_CAGR`와 비교한다.

322개 테스트가 그 위에서 초록이었다. 훅도, 원장 검사도, 20분 전에 같은 파일을
읽은 나도 못 봤다. **본 것은 diff를 읽은 다른 벤더뿐이고, 그게 첫 호출이었다.**

| # | 불변식 | 지키는 것 |
|---|---|---|
| I20 | **연구 경로 변경은 다른 벤더가 랜딩 전에 읽는다** | `check_diff_adversary`, `ORC_DIFF_ADVERSARY=1` |

## 11. 오라클이 실제로 찾은 것 — 2026-09-05

`oracle/`을 만든 날 그것이 산출한 것은 **결함 목록이 아니라 사양의 구멍 네 개**였다.
그리고 그게 이 장치의 값이다: 테스트는 코드와 **같은 미명시 가정**을 인코딩하므로
이 클래스를 원리적으로 못 잡는다.

한 번에 하나씩, 최소 케이스로 좁혀서 확인했다. 매번 **어느 구현이 틀렸는지가 아니라
사양이 무엇을 안 적었는지**가 답이었다.

| # | 브리프 규칙 | 안 적혀 있던 것 | 결정 |
|---|---|---|---|
| 1 | 5 · 청산 | 지갑에 **무엇이 남는가** | **0** (잔존 없음, 거래 중단) |
| 2 | 8 · 비용 | 비용이 **체결가에 있나 별도 차감인가** | 체결가. `qty = 명목/(P·(1+c))` |
| 3 | — · 라벨 | 종료 사유 어휘 | `liquidation·stop·take_profit·max_hold·signal`, `end` 없음 |
| 4 | 1+2 · 재진입 | 청산 **직후 언제** 다시 들어가나 | 청산 봉 `X`의 신호는 무시, `X+1` 신호가 `X+2`에 체결 |

### 11a. 각각을 어떻게 확정했나

**청산 잔존** — 5배 롱이 반토막:
```
fast  1000 → 0.0    1거래, 이후 중단
ref   1000 → 40.4   2거래, 다음 신호 진입
```
0으로 정했다. Binance USD-M 청산은 IOC 주문 + 청산 수수료라 포지션 마진을 가져가고
(7b절), 잔존은 **정확히 유지증거금 가격에 체결**된다고 가정하는데 강제 IOC가 가장 못
받을 가격이 그것이다. KT-2가 `liquidation_rate`를 파산으로 읽고 레버리지 1배 초과를
닫았다. 그리고 데이터가 말 못 할 때 비관적으로 읽는 것이 이 목록의 나머지 전부다.

**비용** — 1000 자본, 5배, 1bp:
```
fast  999.500050   qty = 5000/(P·1.0001)
ref   999.500000   qty = 5000/P,  비용 0.5 별도 차감
```
c의 2차항 차이다. 브리프는 "매수는 P·(1+c)에 체결"까지만 적었고 참조는 별도 차감으로
읽었다. `run_signals`가 사양대로였다.

**재진입** — 매 봉 진입 신호, 4·9번 봉에 청산 신호:
```
fast  (1,5) (7,10) (12,15)
ref   (1,5) (6,10) (11,15)
```
청산 봉 `X`에서 포지션은 **아직 열려 있었으므로** `entry[X]`는 무시된다. 읽을 수 있는
첫 신호가 `entry[X+1]`이고 규칙 1에 따라 `X+2`에 체결된다. 보수적 읽기다 — `X+1`
체결은 그것을 막고 있던 포지션이 살아 있을 때 보인 신호로 진입하는 것이다.

### 11b. 확정된 것 — 두 구현이 정확히 일치하는 경로

최소 케이스로 하나씩 확인했고 전부 `equity` 상대차 **0.00e+00**이다:

```
펀딩(롱·숏)      정확히 일치
스톱             같은 봉, 같은 체결가
익절             같은 봉, 같은 체결가
스톱·익절 동시   둘 다 stop (adverse first)
숏 전반          진입·청산·펀딩 부호
비용             수정 후 일치
청산             수정 후 일치 (둘 다 0)
```

### 11c. 왜 `continue-on-error`인가, 그리고 언제 풀리나

네 구멍이 전부 사양 문제였고 그때마다 브리프를 고쳐 **codex에게 다시 쓰게 했다** —
제가 참조를 고치면 벤더 분리가 무너지고, 그러면 이 장치는 Claude가 Claude를 검증하는
것이 되어 아무것도 안 잡는다.

`orc-guard`에서 오라클이 하드 게이트가 되는 조건은 하나다: **fuzz 400케이스가 0 불일치.**
그때까지는 `continue-on-error`이고, 그 상태로 커밋을 막으면 아무도 결정하지 않은
질문 위에서 전부 멈춘다.

| # | 불변식 | 지키는 것 |
|---|---|---|
| I21 | **불일치는 어느 구현이 틀렸는지가 아니라 사양이 무엇을 안 적었는지로 답한다** | 이 절, 그리고 `oracle/BRIEF.md`의 각 규칙에 붙은 "왜 이 문단이 생겼는지" |
| I22 | **참조는 언제나 다른 벤더가 쓴다** | 브리프를 고치고 재생성, 참조를 손으로 수정하지 않음 |

### 11d. 여섯 번째 구멍, 그리고 한 시드로는 부족했다는 것

400케이스가 0 불일치가 된 뒤 **다른 시드로 3000케이스**를 돌렸더니 1건이 더 나왔다.
한 시드의 400케이스는 충분하지 않았고, 확인하지 않았으면 깨끗하다고 보고했을 것이다.

```
case 1267 (seed 777)  숏 5배, 74번 봉 진입
  fast  77번 봉 청산
  ref   80번 봉 청산
```

77번 봉 펀딩이 **+1.33%**다(퍼저가 만든 극단값). 숏은 그걸 **받으므로** 지갑이 커지고
청산선이 밀린다. 즉 **봉 안에서 펀딩 정산과 청산 검사 중 무엇이 먼저인가**의 문제이고,
브리프는 그것도 안 적었다.

**`fast`가 맞다.** 그리고 이건 이미 원장에 있는 결함 `088134ad0c3b`과 **같은 클래스**다:

> `simulate.py`: 봉 내부 시간 순서가 뒤집혀 있다 — 예정 입금을 먼저 적용한 뒤 같은
> 봉의 저가로 청산을 검사하므로, **나중에 도착하는 증거금이 이미 찍힌 저가로부터
> 포지션을 구해낸다.**

규칙 7에 못 박았다: 봉 안의 순서는 **진입 시점 상태로 청산 검사 → 그 봉의 펀딩 정산**.

| # | 불변식 | 지키는 것 |
|---|---|---|
| I23 | **나중에 도착한 돈이 이미 찍힌 가격으로부터 포지션을 구하지 않는다** | `simulate.py` 1단계, `signal.py`, 브리프 규칙 7 |
| I24 | **오라클은 시드를 바꿔가며 돈다.** 한 시드의 400케이스는 "깨끗하다"의 근거가 아니다 | `--seed`, guard는 400 + 손으로 3000 |
| I25 | **구멍을 메울 때는 재작성이 아니라 편집을 요청한다** | 브리프의 "When a gap is found" 절 |

### 11e. 여섯 라운드에서 배운 것 — 재작성은 분산을 만든다

브리프를 고칠 때마다 프로바이더에게 새로 넘겼고, 매번 **파일 전체를 다시 썼다.**
그 결과:

```
라운드 1~4   구멍 네 개를 하나씩 메움
라운드 5     400케이스 clean, 3000케이스에서 1건 (여섯 번째 구멍)
라운드 6     규칙 7을 고치면서 5라운드가 맞혔던 스톱을 깸  ← 퇴행
```

수정 하나에 구현 하나를 통째로 바꾸면, 오라클은 **사양이 아니라 최신 재작성본**에
대해 불일치를 보고하기 시작한다.

→ 첫 판이 나온 뒤에는 **자기 이전 파일을 보여주고 최소 편집을 요청**한다. 벤더
분리는 그대로다 — 보여주면 안 되는 것은 `orc/eval/signal.py`이지 프로바이더 자신의
출력이 아니다.

참조를 **손으로 고치는 것만은 여전히 금지**다. 사람이 패치하는 순간 구현과 참조의
작성자가 같아지고, 이 장치 전체가 자기를 검사하는 것이 된다.

## 12. 오라클 수렴 — 2026-09-05

```
7,500 케이스, 4개 시드, 불일치 0   →  orc-guard에서 하드 게이트
```

5절이 Track A에 요구하는 이중 평가기를 Track B가 갖게 됐다. 이제 Track B에서도
"두 평가기가 어긋나면 프로젝트의 모든 결과가 무효"가 문장이 아니라 게이트다.

### 12a. 산출물: 사양 구멍 7개, 결함 1개

| 규칙 | 안 적혀 있던 것 | 결정 |
|---|---|---|
| 5 | 청산이 지갑에 무엇을 남기나 | **0**. 잔존 없음, 거래 중단 |
| 8 | 비용이 체결가인가 별도 차감인가 | 체결가. `qty = 명목/(P·(1+c))` |
| — | 종료 사유 어휘 | 다섯 개, `end` 없음 |
| 2 | 재진입이 언제 체결되나 | 청산 `X` → 신호 `X+1` → 체결 `X+2` |
| 1 | 마지막 봉에는 `i+1`이 없다 | `entry[n-1]`은 아무것도 열지 않음 |
| 7 | 봉 안에서 펀딩과 청산검사 순서 | **청산검사 먼저**, 진입 시점 상태로 |
| 9 | 청산된 거래가 보고하는 펀딩 | 실제 발생분. `0`이 아니다 |

결함은 하나: `_PRIORITY`에 `max_hold`가 없어 시계로 닫힌 포지션이 `signal`로
라벨됐다.

**규칙 7과 9는 이 프로젝트가 다른 평가기에 대해 이미 기록해둔 결함과 같다** —
`088134ad0c3b`(나중 증거금이 이미 찍힌 가격에서 구해냄)와 `6641f54ee642`(청산
거래의 쿠폰과 가격 레그가 어긋남). **Track B는 둘 다 안 갖고 있었고 아무도 몰랐다.**

규칙 9가 가장 읽을 만하다: equity가 296봉에 걸쳐 `1.07e-15`로 일치하고 **보고된
총액만** 달랐다. 계좌에서 맞고 리포트에서 틀린 숫자도 틀린 숫자다 —
`funding_collected`는 기록되는 지표다.

### 12b. 성질 테스트가 처음으로 스스로 잡았다

```
RuntimeError: 거래 로그가 equity 곡선과 맞지 않는다:
  booked 36,037,859,999,031,504.00   moved ...496.00
```

차이 8, float64 ULP는 약 4. 정합성 검사의 허용치가 `max(1e-6, 1e-9 × 자본)` —
**절대값**이었다. 같은 돈의 float64 합 둘은 돈이 커지면 1e-6까지 일치할 수 없고,
정상 경로(35배 오른 심볼에 레버리지)에서 평가기가 예외를 던졌다.

허용치가 **비교 대상 크기**를 따라가도록 고쳤다. 원래 잡으려던 것은 여전히 잡힌다 —
10,000 지갑에 −22,200을 기록한 클램프는 상대오차 1.2이지 1e-9가 아니다.

### 12c. 패널 캐시

`run_hypothesis`가 `(symbol, clock)`으로 키를 잡고 `with_positioning`을 안 넘겨서,
미결제약정을 읽는 규칙이 격자 전체에서 `UnsupportedConfig`였다. **H0023이 큐에 있고
전부 스킵으로 기록될 뻔했다.**

```
전  evaluated 0,  skipped 45
후  evaluated 45, skipped 0
```

포지셔닝은 **로드 인자가 아니라 키**에 들어간다. `(symbol, clock)`만으로 키를 잡으면
혼합 격자에서 먼저 도착한 패널이 두 번째 규칙에도 간다 — 같은 결함이 한 칸 옆으로
간 것뿐이다.

### 12d. 게이트 조건

`orc-guard`가 **시드 두 개 × 800케이스**를 돌리고 불일치가 하나라도 있으면 실패한다.
조건은 충족되기 **전에** 적어뒀다(11c절). 시드를 둘로 한 이유는 11d절 그대로다 —
한 시드 400케이스가 clean이라고 보고했고 다른 시드가 1,267번 케이스에서 진짜 구멍을
찾았다.

## 13. 막고 있던 결함 3건 — 2026-09-05

`blocked`가 두 시간 넘게 찍히던 그 3건이다. 셋 다 진짜였고, **셋 다 스위트 323개가

### 13a. 주석이 코드가 갖지 않은 동작을 설명하고 있었다

`cci_mtf`의 청산 절에 이렇게 적혀 있었다:

> 필터가 부호를 바꾸려면 밴드를 통과해야 하므로, 플립은 부호 붙은 절이 잘못된 쪽으로
> 읽히기 전에 **언제나** 잡힌다.

`filt`는 느린 캔들에서 옮겨온 **계단함수**다. 연속한 두 느린 캔들이 밴드 전체를
건너뛸 수 있고, 그 사이에 `|filt| < filter_level`인 바가 하나도 없을 수 있다.
H0019가 등록한 모양 그대로 재현:

```
filt   [150 150 150 150 150 -150 -150 ...]
exit   [  0   0   0   0   0    0    0 ...]   ← 부호가 뒤집혔는데 청산 0건
```

`|filt|`가 계속 150이라 `trend_gone`이 안 뜨고, 그 다음부터 `sign(filt) * base`가
**진입한 방향의 반대**로 측정된다. 포지션이 자기 규칙이 지정한 청산을 뚫고 유지된다.

→ **부호 반전 자체가 regime 종료다.** 밴드 안에 보이는 바가 있었든 없었든.
바 대 바 부호 비교는 상태를 안 들고 하므로 생성기가 자기 포지션을 모른다는 성질도
유지된다.

### 13b. 같은 수정을 한 평가기만 받았다

`analytic.py`는 같은 날 아침에 `ends0 > starts0` 가드를 받았고 `simulate.py`는
못 받았다. `Panel.bars(days)`는 음수를 그대로 통과시키고 격자와 평가기 사이에
검사가 없다.

```
SimSpec(contribution=100, stride_bars=10, n_contributions=5, hold_bars=-30)
  → 등록된 5회 납입 중 2회만 집행,  invested=200 vs 등록 500
hold_bars=-100
  → horizon_bars=-60, 루프가 0바를 돌고 완결된 결과 dict 반환
  → close[starts + H]를 음수 인덱스로 읽어 배열 끝(미래)의 가격을 집음
```

`hold_days`는 자유 그리드 축이고 H0009·H0011이 실제로 열거했다.

### 13c. 카운터가 자기 주석이 고쳤다고 주장한 것을 안 고치고 있었다

`holdout.py` 모듈 주석:

> 한 번의 opening이 972셀 격자를 덮을 수 있고 로그는 1이라고 적을 것이다.

그리고 계속 **로드**를 셌다. `run_trial(cfg, p=...)`는 이미 로드된 패널을 받으므로
로드 한 번이 격자 전체를 덮는다. 리뷰가 단일 read 아래 83셀을 채점해 보였다.

수정 후, 리뷰어의 트리거 그대로:

```
실제 평가한 셀        58
n_sealed_reads         1   ← 로드
n_sealed_measurements 58   ← 측정 (이전엔 존재하지 않던 필드)
```

**평생 3번뿐인 opening이다.** 로그는 각각이 실제로 무엇을 봤는지 말해야 한다.
개발 패널에서는 조용하다 — 하루에 수천 번 측정되고 그중 무엇도 봉인을 본 것이 아니다.
